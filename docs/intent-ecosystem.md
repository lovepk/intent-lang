# 应用场景与生态 (Scenarios & Ecosystem)

> 本文回答两个问题：**IL 这套东西能用在哪些场景**、**如何围绕它建立生态**。
> 属于愿景/方向性文档；语言本体的硬规则见 `intent-spec.md`，目标与非目标见 `intent-goals.md`。

---

## 1. 核心价值

一句话：**把"意图"变成独立于会话、可移植、可复现、可审计的资产。**

现有对话式 LLM 的四个结构性缺陷（详见 `intent-goals.md` §3）——意图易失、对话不可移植、输出不可复现、意图无档案——都源于"意图只活在会话里"。IL 把意图抽出来，变成一份可像代码一样 diff / commit / 回滚 / 交付的档案，由此展开全部场景。

---

## 2. 应用场景

### 2.1 跨会话 / 跨模型的持续开发
现在换模型或新开会话就得从头描述需求。用 IL：档案是唯一持久资产，任意 LLM 只凭【规范 + 档案】就能接着干，并能复现既有成果。适合长周期项目、模型迭代频繁的团队。

### 2.2 去厂商锁定 / 可移植交付
`il repro --key B` 已演示：同一份档案喂给不同模型，ACCEPT 行为验收均通过。交付物不再是一坨代码，而是**档案**——任何人可用任意模型重建。企业可据此避免被单一模型供应商锁定。

### 2.3 可复现构建（意图层的 Nix）
`repro + accept + SNIPPET` 构成"给定档案 → 得到行为/形态一致产物"的闭环：
- 默认行为一致（ACCEPT 逐条验收）；
- 点名形态一致（SNIPPET 原文逐字出现）。
适合对复现性有硬要求、又希望引入 LLM 的构建/交付流水线。

### 2.4 非程序员的规格交付
IL 人类可读优先（原则 4），产品、业务、客户能读懂甚至书写意图，LLM 负责实现与验收。降低"需求 → 实现"的翻译损耗与歧义。

### 2.5 审计 / 合规 / 知识沉淀
commit 链让每条需求可追溯来源、可 diff、可回滚（见 `intent-commands.md` 的 `log/show/rollback`）。适合受监管行业、团队交接（不必翻聊天记录）、教学与经验沉淀。

### 2.6 模板与共享规范复用
`<ref: 档案名#条目ID@版本>` 已能引用公共档案（见 `intent-spec.md` §2.6）。可沉淀"公司错误处理规范""UI 风格档案""基础库行为"等，各处**引用而非复制**，版本锁死、避免多处漂移。

---

## 3. 如何建立生态

按 **语言 → 工具 → 资产 → 网络 → 治理** 五层递进。当前项目大致只在 L1。

### L1 语言与工具（已有雏形）
- **已有**：规范 v2.0、parser / lint / diff、CLI 9 命令、VS Code 语法高亮。
- **缺**：formatter、LSP（`<ref>` 跳转、编号补全、实时 lint）、稳定的规范版本化与 RFC 流程。

### L2 Provider 生态
- 把 `provider.Provider` 接口开放为插件（OpenAI / Claude / 本地模型等）。目前已支持 DeepSeek，接口已抽象，扩展成本低。
- 目标：让"档案可移植"成为跨模型的常态，而非单模型巧合。

### L3 档案资产市场（生态的种子）
- 建**档案注册表**：像 npm / crates 一样发布、按名 + 版本拉取档案。
- `<ref>` 的"版本锁死"正是包管理语义，天然可长成依赖系统。
- 分类：公共规范档案、领域模板、可复用组件行为。

### L4 平台与集成
- 托管档案仓库 + 托管复现 / 验收服务。
- **CI 集成**：每次 commit 自动跑 `lint → repro → accept`，把"复现性"做成可门禁的指标。
- 与 Git 打通：档案进仓库，PR 审的是**意图 diff**。

### L5 治理与社区
- 规范版本治理（RFC）、兼容性承诺、FIDELITY 量化标准。
- 示例库、最佳实践、公开 benchmark（同一档案多模型的验收通过率）。

---

## 4. 务实的切入点

不建议一上来铺平台。优先级建议：

1. **固化规范 + 打磨工具链**（LSP / formatter）——生态的地基。
2. **多 Provider**——证明档案可移植。
3. **公共档案库 + `<ref>` 版本依赖**——最小的"生态网络"。
4. **CI 复现门禁**——让价值可被验证、可被依赖。

> 一句话：**先让"档案"成为可信、可交换的标准格式，生态才会围绕它自然生长。**
