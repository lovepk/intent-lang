# IL 意图语言规范 (Intent Language Spec) — v2.0

> 本文既是给人类工程师的实现依据，也是**原样注入给 LLM 的语言规则**（或它的权威来源）。
> 语言的五条根本原则必须被 LLM 理解，否则后续语法毫无意义（**原则 0 是最重要的一条**）。
> **想快速看懂一份档案/查关键词的人**，请看 `il-keywords.md`（人类速查手册）；本文是完整规范。

---

## 0. 语言定位

- **书写者**：LLM（主要）；**读者**：LLM（主要）+ 人类（审计）。
- IL 是**自包含规格语言**，不是通用编程语言。它不是被"执行"的，而是被"消费"的：复现端 LLM 读它并重建产物。
- 唯一目的：让**任意** LLM（从未参与原对话）仅凭【规范 + 档案 B】重建出与原产物**意图一致**的结果——默认行为一致（ACCEPT 验收），点名锁定的部分形态一致（见原则 3）。
- 语法上：**强模板、弱语法**。段结构是强制的、稳定的；条目内容是自然语言句子，但必须是"已消歧的事实"（见原则 1）。

## 1. 根本原则（五条；原则 0 最重要）

### 原则 0（最高原则）：记录优先，不干扰生成（Record, Don't Interfere）
IL 是**记录介质**，不是控制手段。它的唯一职责是**如实、合法、自洽地记录**意图及其演化；它**不得**被用来约束、否决、阻断或改写 LLM 的生成。

由此推出：
- 生成端**自由产出**；系统只记录——不因内容而拒绝、不重试、不扣留、不提示。
- 档案的合法性/自洽性由**系统分层保证**（L1 确定性构造 + L2 记录员规范化），而不是靠"拒绝模型"来换取。
- 一致性靠**"记录完整 + 可核对"**保证，而不是靠"阻断不一致"。

> 为什么最重要：原则 1–4 约束的是"档案里写什么"，原则 0 约束的是"语言与 LLM 的关系"。一旦语言开始干扰生成，它就退化成控制协议，而不再是意图的记录——其余原则也随之失去意义。因此它是前提。

### 原则 1：消歧优先（Disambiguation over Description）
LLM 之间结果不一致，根因不是"没听懂功能"，而是**在每一个没说死的地方各自做了选择**。
因此 IL 只允许存在**已消歧的事实**；凡是不能收敛到"任何 LLM 都只能得到一个实现"的内容，一律禁止进入核心段，必须显式留在 `OPEN` 并携带默认值。

> 判定标准（写每一条 CONTRACT 前自问）：
> "任意一个陌生 LLM，看到这条，能否不假思索地写出同样的代码？"
> 不能 → 要么继续消歧，要么降级到 ANCHORS，要么放进 OPEN。

### 原则 2：否决与决策是资产（Negative Constraints & Decision Log）
对话中被否决的选项（"不要运算符优先级"）和做过的决策，比肯定描述更能锁死产物。
复现端最大的风险是"自作聪明"把当初砍掉的选项重新发明回来。
因此 IL 必须能表达**显式否定**，且保留**决策日志**。

### 原则 3：锁定层级决定语言重量（Fidelity is Declared, not Implicit）
"意图一致"分三层，复现端的自由空间天差地别：

| FIDELITY | 期望的"一致" | 复现端被允许的自由 | 语言需要的强度 |
|---|---|---|---|
| `behavior` | 行为一致（同输入同输出） | 实现文本/结构自由 | 轻：CONTRACT + ACCEPT 足够 |
| `structure` | 行为 + 模块/接口/结构一致 | 命名、细节自由 | 中：需补结构级 ANCHORS/SNIPPET |
| `artifact` | 连形态（布局/命名/UI 细节）都一致 | 几乎无自由 | 重：必须含 SNIPPET 黄金代码，近乎照抄 |

档案**必须**显式声明 FIDELITY。默认期望是 `behavior`（行为验收即可），**"形态一致"只对档案点名锁定的部分生效**（如 SNIPPET 覆盖的代码块、ANCHORS 约束的布局），不被点名的实现细节允许不同、不视为复现失败。不声明即视为 `behavior`，不得虚报。

### 原则 4：人类可读优先于机器语法（Human-Readable First）
IL 的**书写者和解释者都是 LLM，但读者中永远包括人类**——且可以是完全不懂编程的人（产品、业务、客户）。
由此推出两件事：
1. IL **永不追求"可编译的文法"**。它不存在语法错误，只存在"说没说死"。语义靠原则 1 的消歧判定保证，不靠文法规则保证。
2. 所有传统语言的语法要素，在 IL 里**必须以自然句子的形态出现**，禁止以代码形态出现（见第 2.5 节对照表）。读不懂的地方就该是一句中文，而不是一段符号。

> 一句话红线：**任何一行，如果非程序员需要"学过编程"才能看懂，它就是设计失败。**

## 2. 档案骨架（强模板，段落顺序固定）

```
# file: calculator@1.0.0              ← 注释行，供人阅读
INTENT calculator@1.0.0               ← 产物名@版本
KIND program                          ← program | document | service | ...
FIDELITY artifact                     ← behavior | structure | artifact（必填）
TARGET python@3.12, single-file, tkinter-grid

CONTRACT
  R1: add(a,b) -> a+b
  R2: divide(a,b) -> a/b; guard b!=0 raise ZeroDivisionError
  R3: evaluation follows input order; NO operator precedence   ← 显式否定
  R4: expression grammar is flat binary ops with = as terminator

ANCHORS
  in: "2+3x4="   out: "20"
  style: calc logic pure functions; ui layer separate; snake_case

SNIPPET eval_core        ← 黄金代码：最高强度锚点，仅 artifact/structure 层使用
  <不可折叠的实现原文：关键函数、布局结构……>

ACCEPT
  A1: add(1,2) == 3
  A4: divide(1,0) raises ZeroDivisionError
  A5: run "2+3x4=" displays "20"

DECISIONS
  D1: 无运算符优先级         reject: 先乘除后加减      due: R3 用户明确要求
  D2: 单文件部署            reject: 多模块             due: 便于直接运行演示

OPEN
  ?1: 除零错误在 GUI 上的呈现方式     default: display "Error"; A4 不受影响

META
  spec: v2.0
  created: 2026-09-06T00:00:00Z
  commits: 3
  deprecated: []
```

### 2.1 文件后缀与命名（规范）

- **官方文件扩展名：`.il`**。档案文件一律使用 `.il`；目录/仓库默认名沿用 `.il`（见 03-design）。
- 一份档案文件 = 一个产物。文件名建议与 `INTENT` 的产物名一致（小写、连字符分隔），如 `INTENT calculator@1.0.0` → `calculator.il`；带版本快照可用 `calculator.1.0.0.il`。
- 文件可带可选的 `# file: <产物名>@<版本>` 注释行作为人类可读标识（骨架示例第一行）；解析器忽略之，不以它为准。
- 产物源文件（复现输出）不得用 `.il` 扩展名，避免与档案混淆；CLI 按 TARGET 推断 `.py`/`.go`/`.js` 等。

### 2.4 排版文法（解析器依赖，必守）

- **段头与头部字段必须顶格（行首无缩进）**；只有顶格行才可能开启新段。
- **段内容一律缩进**（规范格式统一 2 空格）。解析器以"是否缩进"区分内容与段头。
- **SNIPPET 的原文在规范格式中统一缩进存储**（每行加 2 空格前缀），消费端负责反缩进还原。SNIPPET 内容行即使形如关键词（如 `META 42`）也因带缩进而不会被误判为新段头——这是"SNIPPET 可含任意文本"承诺的解析保证。
- 解析器对顶格行做白名单段名匹配；SNIPPET 段遇到下一个顶格的合法段名才结束。

### 2.5 语法要素对照表（传统语言 → IL 的自然形态）

IL 有语法，但没有"代码样"的语法。每个传统要素都有非程序员可读的对应物：

| 传统语言要素 | IL 的形态 | 人类看到的示例 |
|---|---|---|
| 关键词 | 全大写自然词段名 | `CONTRACT:` `ACCEPT:` |
| 条目/语句 | 编号前缀 + 一个事实句 | `R1: 加法 -> a+b` |
| 条件结构 (if) | 句首状语"仅当…"、"当…时" | `R5: 仅当 FIDELITY=artifact 时…` |
| 变量/引用 | 自然词"见 Rx" | `R2: 输入格式见 R1` |
| 取反/否定 | "不/禁止/不做" | `R6: 不做运算符优先级` |
| 类型声明 | 自然词 + 量词 | `输入是十进制数` |
| 返回值 | 箭头 `->` | `add(a,b) -> a+b` |
| 函数/过程 | 段 + 编号 + 输入输出句 | `SNIPPET` 段、`R` 条目 |
| 嵌套块/作用域 | **禁止** | 一律平铺清单 |
| 语法错误 | **不存在** | 只有"没说死"（违反原则 1） |

规则：段落与编号是唯一"硬"结构；其余全部是自然语言句子。若某个语义用代码写更容易，就写中文句子把它说死，而不是引代码语法。

### 2.6 跨档案引用（v2 新增语法元素）

- **用途**：某条行为/验收/示例属于另一个档案（共享规范、公共错误处理、基础库行为）时，**引用而非复制**，避免多处维护漂移。
- **语法**：`<ref: 档案名#条目ID@版本>`，嵌在条目正文里。例：`R3: 错误处理遵循 <ref: common#R3@1.2>`。
- **可出现在**：`CONTRACT` / `ACCEPT` / `ANCHORS` 的条目里。
- **禁止出现在**：`DECISIONS` / `OPEN` / `META`（决策与待定项是档案私有）。
- **版本必填**：引用锁死被引档案版本；被引档案更新不自动影响引用方，跟进需显式改 `<ref>` 版本。
- **本地补充允许**：`<ref>` 只嵌入目标条目原文，可在其前后写本档案的本地约束。
- **两层档案**：源档案（含 `<ref>`，人/AI 维护）与展开档案（机器把 `<ref>` 递归摊成自包含文本，喂 LLM 复现用）。LLM 复现端永远只见自包含的展开档案——"失忆后仅凭 B 可复现"承诺不变。
- **展开产物标注来源**：物化后附 `（来源: 档案名#条目ID@版本）`，可审计、不会被再扫描为引用。

## 3. 段定义（语义 + 消费规则）

### 3.1 头：`INTENT` / `KIND` / `FIDELITY` / `TARGET`
- `INTENT <name>@<ver>`：产物身份，复现端产物文件名默认取自这里。
- `KIND`：产物大类，决定复现端以何种姿态生成。
- `FIDELITY`：**必填**，声明锁哪一层（见原则 3）。复现端必须按该层交付，相似度工具按该层评分。
- `TARGET`：技术栈与形态约束——**全局最大的漂移源，必须尽量锁死**。留空等于放权，放权 = 复现端自由选择 = 漂移。

### 3.2 `CONTRACT`（契约——已消歧的约束，核心段）
- 每条 `R<n>`：稳定编号 + 一句话事实。
- 编号语义：**新增=追加**；**修订=改正文保编号**；**作废=移除并把编号记入 META.deprecated**。编号永不复用。
- 允许 `NO`/`NOT` 显式否定（原则 2 的直接载体）。
- 描述格式自由，但必须满足原则 1 的判定标准；描述不清时用 ANCHORS/SNIPPET 兜底，而不是在 CONTRACT 里写模糊话。
- **消费规则（复现端）**：每一条 R 都必须被落实为产物中的对应实现；做不到 = 复现失败，不是"近似"。

### 3.3 `ANCHORS`（锚点——给复现端的示例与风格）

**与 ACCEPT 的分工（写档案时先判断该用谁）**：
- `ACCEPT` 是**给验收引擎的机器可判定断言**——产物要逐条被跑/被判定。
- `ANCHORS` 的 `in/out` 是**给复现端 LLM 的形态示例**——用来收敛"实现长什么样"，不要求机器执行。
- 规则：**同一行为能写成可判定的断言 → 写 ACCEPT；写不判定、但要给复现端"照着做"的形态样板 → 才放 ANCHORS in/out**。不要同一行为两处重复。
- 例外：ACCEPT 里某条只给了文字断言、没给具体输入输出形态时，可在 ANCHORS 补一条 in/out 示例帮助复现端，此时 ANCHORS 是 ACCEPT 的"形态补图"而非重复。

条目：
- `in: <输入示例>` / `out: <输出示例>`：一个形态样板。对 LLM 的收敛力**远强于**等量描述文字（LLM 靠示例泛化）。可多条。
- `style:`：命名、结构、口味的一句话约束。
- **消费规则**：产物应体现这些示例与风格；如某 in/out 实际是对 ACCEPT 行为的形态补图，最终仍以 ACCEPT 判定为准。

### 3.4 `SNIPPET`（黄金代码——artifact/structure 层专用）
- 段名 `SNIPPET <label>`，段体是**原样、不可折叠的实现原文**（关键算法、UI 布局、配置……）。
- 可多个。它是最高强度的锚点：复现端应当**忠实迁移**而非改写。
- **消费规则**：出现在产物中时，结构/关键逻辑必须与该片段逐行对应；允许的差异仅是"夹住它的外围胶水"。

### 3.5 `ACCEPT`（验收用例——可判定真/假）
- 每条 `A<n>`：可执行/可判定的用例（人工可跑、脚本可跑、或 LLM 可自评的断言）。
- **消费规则**：复现端交付前必须自检所有 A 通过；相似度报告逐条打钩。

### 3.6 `DECISIONS`（决策日志——原则 2 的载体）
- 每条 `D<n>`：`<一句话决定>  reject: <被否决选项>  due: <起因/用户原话>`。
- **简洁性**：每条只允许一句话的结论表达，禁止长篇推理、自言自语、推演过程。档案只记录结论，不记录"我考虑/或者/可以改成"这类思考流。
- **reject 语义（重要）**：`reject:` 只写【本次讨论中提出过、被否定的备选方案】，**禁止写"改动前的旧状态"**——旧状态不是备选，写进去会让复现端误读成"该功能被禁"并诱发假冲突。新决定应涵盖旧状态的全部合理行为。
- **消费规则**：复现端**不得**把 reject 中的选项重新引入。若发现 CONTRACT/ACCEPT 与某条 reject 冲突（档案自相矛盾），按"reject 优先不实现"处理并在交付说明中标注，绝不自行二选一；真正的决策推翻须由一次新对话完成（写回新 D）。

### 3.7 `OPEN`（开放项——尚未消歧）
- 每条 `?<n>`：一个未决问题的简明表述 + `default:` 一句话默认处理。
- **消费规则**：复现端按 default 处理即可，**不做创造性发挥**，并在交付说明中列出使用了哪些 default。
- 后续对话可以把 OPEN 项收敛为 CONTRACT/DECISIONS（消除一个自由度），OPEN 越少档案越"熟"。

### 3.8 `META`（归档元信息——完全由 Agent 维护）
- `spec`：本规范版本。`created` / `commits`：档案生命周期。`deprecated`：作废的 R 编号。
- **LLM 端不可见**：注入给 LLM 的档案剥离 META 段（Agent 侧 `StripMeta`）；LLM 被明确禁止输出 META。收到 LLM 输出后由 Agent 依据 diff 计算 `deprecated`、`commits` 并重建 META 写入 commit。← 真实验证结论：模型会篡改 META（如把 commits 改成 0），因此 META 不能交给模型。

### 3.9 注释
- `#` 开头行为注释，LLM 可用于说明任何条目（如"这条为什么这么写"），不影响语义。

## 4. 档案编辑规则（给写档案的 LLM：像程序员改代码）

1. **全量重写**：一次用户消息 = 输出完整的新档案文本（含未改动段落）。**禁止输出片段/patch**；diff 由 Agent 程序化生成并入库。← 保证"档案自包含，失忆后仅凭 B 可复现"这个硬约束。
2. **改动最小化**：只动必要行；未变段落逐字保留（含注释）。
3. **落在正确段**：加功能→`CONTRACT` 新 `R`；改行为→改对应 `R` 正文 + 同步 `ACCEPT`/`ANCHORS`；用户给了否定→落成 `NO …` 或新增 `DECISIONS`；更细的形态需求→补 `SNIPPET`/`style`；还没定→放 `OPEN` 并给 `default`。
4. **用户消息与产物无关**（闲聊/提问/确认）：`IntentUpdate` 为空，不产生 commit。
5. **冲突处理**：用户新意图与旧档案冲突（如"改成减法优先"）→ 修订对应 `R`、更新 `ACCEPT`、原 `D` 记新决策或作废，不允许档案里残留互相矛盾的两条事实。
6. **FIDELITY 变更**：若对话把需求从 behavior 推向 artifact，必须同步把 FIDELITY 改到对应层，否则复现端不会知道自己需要多忠实的产出。

## 5. 复现指令（给复现端 LLM 的固定系统提示）

> 你是产物重建器。下面是一份按 IL 规范 v2.0 书写的意图档案。
> 请按 `FIDELITY` 声明层重建产物（`KIND`/`TARGET` 指明形态）。
> 规则：
> 1. CONTRACT 每条必须落实，不得省略，不得添加档案之外的需求；
> 2. 让所有 ACCEPT 用例成立；交付前自检；
> 3. ANCHORS 的 in/out 必须满足、style 必须遵守；
> 4. SNIPPET 的内容必须忠实迁移；
> 5. DECISIONS 中 reject 的选项不得引入；
> 6. OPEN 项一律按 default 处理，不做发挥，交付时列出所用 default；
> 7. FIDELITY 是 behavior 时允许自由实现，是 artifact 时尽可能逼近原始形态。

## 6. 语言完整性自检（Agent 校验用）

解析器只做"轻校验"（强模板、弱语法，不追求精确文法），但必须拦下这些硬伤：

- 头四段齐全：`INTENT/KIND/FIDELITY/TARGET`；`FIDELITY` 取值合法。
- `CONTRACT` 编号唯一且递增；`ACCEPT`/`DECISIONS` 编号唯一。
- 正文无"空段"（有段名无条目 = 结构残缺）。
- `OPEN` 项都带 `default:`。
- 同一 R 的正文在整份档案中只出现一次（防粘贴重复）。
- META 不存在于 LLM 输出校验范围：Agent 注入前剥离，校验目标文档本就不含 META；存储时由 Agent 依据 diff 重建。

---

## 7. 设计问答（为什么要这样设计）

**Q: 为什么允许自然语言条目，而不是强制结构化？**
A: 书写者是 LLM。强制精确文法的语言，LLM 会高频违例，违例即失忆。用"强模板锁结构 + 自然语言锁事实"，LLM 最容易稳定产出；消歧靠原则 1 的判定标准，不靠语法。

**Q: 为什么 OPEN 必须带 default？**
A: 复现端永远不该"做决定"。不给 default，复现端就会自由发挥，漂移随即发生。default 让 OPEN 也变成确定的。

**Q: 为什么需要 SNIPPET，描述清楚不就行？**
A: 不行。UI 布局、复杂算法、边界行为的精确语义，用自然语言描述的信息量远低于原文。当用户点名要求"这部分长得也一样"时，唯一可靠路径是把原文嵌进档案。SNIPPET 只锁定被点名的部分，其余靠行为验收——这是原则 3 的直接推论。

**Q: 为什么编号永不复用、删除要记 deprecated？**
A: 档案要有可审计的演化史（diff/回滚依赖它），且历史 ACCEPT/commit 要能解释。编号是跨版本引用和追溯的锚点。
