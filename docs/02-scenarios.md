# 场景文档 (Scenarios)

本文描述 intent-lang 要支撑的核心场景。每个场景都写成"可演示、可验证"的形式，作为后续实现与验收的输入。

## 场景 1：核心闭环 —— 计算器（Golden Path）

> 目标：证明"双通道对话 + 失忆后可复现"成立。

1. 用户新开会话，agent 把 **IL 规范** 注入给 LLM-A。
2. 用户说："做一个计算器，支持加和减。"
3. LLM-A 正常回答（给出/描述计算器 C 的当前实现），**同时**写出一份意图档案 `B@v0.1`（CONTRACT: add/subtract）。
4. 用户说："加上乘法。"
5. LLM-A 正常回答，并**像改代码一样把 B 更新为 `B@v0.2`**（+multiply），本次变更形成一条 commit（含 diff、commit message、关联用户消息）。
6. 用户说："把命令行交互改成 GUI（tkinter，网格布局）。"
7. LLM-A 更新 `B@v1.0`（+GUI、布局约束、验收用例；GUI 布局经 SNIPPET 点名锁定），产物 C 完成。
8. **删除 session**（人机双失忆）。
9. 新开会话，把【IL 规范 + `B@v1.0`】交给 LLM-B（可与 A 是不同模型）。
10. LLM-B 重建产物 C'。
11. 双轨验收：(a) 用 ACCEPT 用例对 C' 做行为验收，逐条判定；(b) 对被 SNIPPET 点名的部分做文本/结构对比。

成功判据：C' 的 ACCEPT 行为用例全数通过；被 SNIPPET 点名的部分（GUI 布局等）结构/文本相符。未点名的实现细节允许不同，不视为失败。

## 场景 2：跨模型迁移

> 目标：证明"意图档案是标准交换格式"，换 LLM 不需要重述需求。

- 档案 B 由 LLM-A（模型甲）写成。
- 复现时交给 LLM-B（模型乙，从未参与过原始对话）。
- 判据：仅凭【规范 + B】，模型乙重建的 C' 通过 ACCEPT 行为验收、点名锁定部分相符，且不需要任何额外解释。

## 场景 3：档案演化与回滚（像 Git 一样）

> 目标：证明档案 B 是可版本化的代码资产，不是流水账。

- 回放 B 的 commit 历史：每条 commit 应能对应到一次用户消息。
- 回滚到 `B@v0.2`，再复现：应得到"加/减/乘、无 GUI"的合理还原产物。
- 判据：回滚后复现产物与对应历史状态语义一致。

## 场景 4：对话中断续写（未失忆场景下的续接）

> 目标：agent 在会话仍存在时，也可直接从当前档案继续，不必重读整段历史。

- 用户隔天回来："上次那个计算器，再加个开平方。"
- 即使 agent 不加载历史消息，只要加载【规范 + 最新 B】，LLM 就能继续正确更新 B。
- 这展示 B 同时是"session 失效时的记忆"和"session 存在时的压缩上下文"。

## 场景 5：多产物档案库（远期）

> 目标：多个项目各自的 B 组成一个档案库，长期可检索。

- 每个意图档案有元信息（产品名、版本、状态）。
- 后续可作为工作区级别的记忆库被 agent 查询。
- 第一阶段只保证单档案的读写格式预留元信息段，不做检索 UI。

## 场景 6：可执行性验证（产物测试）

> 目标：复现不只是"看起来像"，而是"行为上对"。

- B 中带验收用例（accept）。
- 复现出的 C' 若可运行，则运行其验收用例，得到"通过/失败"的行为报告。
- 第一阶段：当产物为可执行程序时支持该验证；纯概念产物时退化为 diff 报告。
